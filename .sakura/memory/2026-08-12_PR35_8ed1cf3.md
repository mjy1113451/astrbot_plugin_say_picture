## 二、发现的模式

### 2.1 代码模式观察

**优点**：
- 集中式常量管理（`BUBBLE_WIDTH` 等）
- 相对坐标计算便于整体调整

**问题模式**：
```python
# 变量名重复 + 覆盖
badge_tw = font_small.getbbox(...)  # 第 1 处
# ... 省略若干行 ...
badge_tw = badge_bb[2] - badge_bb[0]  # 第 2 处，覆盖旧值
```

### 2.2 架构观察

- **简单清晰**：无复杂依赖，适合 AstrBot 插件定位
- **硬编码布局**：气泡、标签、头像均直接计算坐标，缺乏抽象

## 三、规范完善建议

### 3.1 新增审查规则

**UI 变更专项检查**：

```
□ 极端长度测试（单字符 / 50+ 字符）
□ 多语言兼容性（ASCII / CJK / Emoji）
□ 屏幕适配（最小支持分辨率）
□ 硬编码数值是否有配置化需求
```

### 3.2 建议升级检查单

当前 Quick 模式边界标准未包含：
> **新增复杂计算逻辑（即使行数少）**

本次 LV100 标签绘制涉及多步计算，若逻辑错误会直接影响用户体验。

## 四、经验教训

### 4.1 核心收获

| 教训 | 行动项 |
|------|--------|
| 小改动 ≠ 无风险 | 关注计算逻辑本身的正确性，而非仅行数 |
| 变量覆盖是隐蔽陷阱 | 在代码风格建议中标注"同一作用域内重复赋值"风险 |
| 9/10 评分需说明原因 | 建议在报告中补充"扣 1 分"的明确理由 |

### 4.2 对 Quick 模式的再思考

Quick 模式当前决策树：

```
行数 ≤ 30?
├─ 否 → 升级完整审查
└─ 是 → Quick 审查
```

**建议增加**：
```
├─ 是 → Quick 审查
│   └─ 但需验证：无复杂计算链路
└─ 建议新增判断：
    └─ 若包含 ≥5 步数学运算 → 降级评分或补充测试说明
```

### 4.3 下次审查关注点

1. **数学计算类代码**：用具体数值代入验证（如气泡宽度 = 520 - 40 - 20 = 460）
2. **文本相关计算**：必须测试 CJK 字符等宽特性
3. **硬编码参数**：识别"看似可配置"的常量
