### 2.1 编码习惯

```
特征                        | 观察
---------------------------|------------------

```

### 2.2 架构观察

```
fonts/
├── msyh-subset.ttf  (内置主字体，~6MB)
└── [可能的 noto-sans-sc.ttf]  (网络下载兜底)

加载优先级:
1. 插件内置 → 2. 系统字体 → 3. 网络下载 → 4. PIL 默认
```

**风险点**：网络下载作为第三级兜底，意味着在 Docker 环境下，如果内置字体加载失败，会触发网络请求，而 Docker 网络可能受限。

## 三、规范完善建议

### 3.1 建议新增审查规则

**规则 1：字体/资源内置化审查**

当 PR 引入内置资源文件（字体、图片、模型等）时，必须检查：

```
□ 是否有完整性校验机制（SHA256/MD5）？
□ 是否有大小警告（>1MB 应提示优化）？
□ 是否考虑了用户的磁盘空间？
```

**规则 2：多级回退链路验证**

当代码存在 3 级及以上回退时，必须逐级验证：

```
□ 每级失败是否被 try-except 捕获？
□ 每级失败是否记录日志？
□ 最终兜底是否保证程序可继续运行？
```

**规则 3：quick 策略的例外条件扩展**

```
当前: 网络操作 → 完整审查
建议: 任意 3 项高风险操作组合 → 完整审查
      - 网络操作
      - 文件系统操作  
      - 资源加载（字体/模型/图片）
      - 临时文件创建
```

### 3.2 项目特有规范建议

**AstrBot 插件规范**：

1. **字体加载必须包含内置字体作为最高优先级**（已有）
2. **内置字体必须附带校验文件**（缺失）
3. **网络下载字体必须设置 timeout ≤ 10s**
4. **大型资源文件（>1MB）应要求显式说明必要性**

## 四、经验教训

### 4.1 值得关注的要点

| 教训 | 应用场景 |
|------|----------|
| **quick 模式不应跳过回退逻辑验证** | 存在多级降级的代码 |
| **内置资源必须验证完整性** | PR 引入新资源文件时 |
| **魔法数字应被识别** | avatar_size=90, shadow 参数等 |
| **日志缺失是隐蔽风险** | 静默降级使问题难以定位 |

### 4.2 字体类审查的特定经验

```
字体加载审查清单（必查）:
□ 超时设置
□ 完整性校验（内置资源）
□ 失败日志记录
□ 内存占用评估
□ 多实例场景（是否重复加载）
□ 系统依赖（字体引擎）
```

### 4.3 本次审查的改进方向

**应该追问的问题**：
1. 内置字体损坏时会发生什么？有校验机制吗？
2. 网络下载字体失败时，用户会收到任何提示吗？
3. 如果四级回退全部失败，程序的行为是什么？
4. 6MB 字体在低端设备上的加载时间会影响用户体验吗？
