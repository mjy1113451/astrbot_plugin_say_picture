# astrbot_plugin_say_picture 项目概述

## 1. 项目简介

astrbot_plugin_say_picture 是一个基于 AstrBot 框架开发的 QQ 机器人插件，核心功能是让机器人能够根据用户 @指令 自动生成和发送表情包图片。该插件通过 OneBot v11 协议与 QQ 平台实现交互，支持群聊和私聊场景下的图片消息发送。

## 2. 技术栈

### 核心框架

AstrBot 框架

AstrBot 是一款模块化的 QQ 机器人框架，支持插件化扩展。开发者可通过编写插件实现自定义功能，框架提供了事件处理、消息解析、配置管理等基础能力。

### 通信协议

OneBot v11 标准

插件遵循 OneBot v11 协议规范，通过调用以下核心 API 实现消息发送功能：

send_msg - 发送消息
send_group_msg - 发送群消息
send_private_msg - 发送私聊消息

### 开发语言

Python 3.x

项目代码总量约 6145 行，采用 Python 作为主要开发语言，具备良好的跨平台兼容性和丰富的第三方库支持。

该许可证要求衍生作品必须开源，适用于网络服务场景。

```
astrbot_plugin_say_picture/
├── main.py                 # 插件主逻辑入口，核心功能实现

    ├── memory/             # 运行时内存/缓存数据
```

### 核心模块说明

main.py

插件的主逻辑文件，包含消息处理、指令解析、图片生成与发送等核心功能。插件检测用户 @提及 行为，当触发预设指令时执行图片生成流程。

metadata.yaml

插件元信息配置，定义插件名称、版本号、作者、依赖项等基本信息，框架通过此文件识别和加载插件。

_conf_schema.json

配置文件的 JSON Schema 定义，描述各配置项的类型、默认值和约束条件，用于配置验证和自动生成配置界面。

config.json

用户运行时配置文件，存储插件的可配置参数，如默认图片地址、发送格式（闪照或普通图片）等。

## 4. 开发约定

### 插件开发规范

基于 AstrBot 框架的插件开发模式，插件需提供标准的元信息配置和入口函数。main.py 中应实现框架定义的事件处理接口，响应用户消息和指令。

### 配置管理约定

插件采用 JSON Schema 规范定义配置结构，配置项包含类型声明、描述说明和默认值。_conf_schema.json 提供了配置验证能力，确保运行时配置的有效性。

### 消息交互约定

遵循 OneBot v11 协议的消息格式，图片消息采用 CQ 码或 URL 方式传输。插件支持普通图片和闪照两种发送模式，可通过配置切换。

### 目录组织约定

.sakura/ 目录用于存放运行时资源，采用 docs、memory、rules 子目录分离不同类型资源。docs/ 存放文档，memory/ 存放运行时数据，rules/ 存放业务规则。

### 许可证遵循

项目采用 AGPL-3.0 许可证，所有分发和修改需遵循开源要求。网络使用场景也需开源相关代码，贡献代码默认接受相同许可证约束。

## 5. 常见问题模式（基于反思累计 5 次）

### 图片生成类 Issue
- **中文渲染问题**：字体路径跨平台差异大（Windows: `C:/Windows/Fonts/simhei.ttf`，macOS: `/System/Library/Fonts/PingFang.ttc`，Linux: 需fontconfig）
- **气泡框位置**：需考虑内容长度动态变化，避免溢出
- **截图分析**：信息损耗难以避免，提取信息时建议注明"基于截图推测"

### 标题异常处理
- 空标题/仅标点标题（如"."）是常见情况，必须依赖摘要分析
- 建议在无标题时自动使用摘要首句作为标题

### 技术风险点
- **协议标签过滤**：摘要生成时需过滤 `http://`、`javascript:` 等协议标签，防止验证失败
- **分类识别**：含 `[bug]` 关键词的标题应优先识别为 bug
- **重复检测**：duplicate Issue 应在分析中明确告知用户升级链接或行动项

### 标签体系建议
| 标签 | 适用场景 |
|------|---------|
| `font` | 字体相关问题 |
| `chinese`/`i18n` | 中文字体/国际化问题 |
| `ui`/`ux` | 用户界面调整 |
| `display` | 显示位置相关 |
| `good-first-issue` | 改动简单适合新人 |
| `duplicate` | 重复问题（需附升级指引） |

### 优先级判断
- 优先级不应仅依据实现难度，需综合考虑：用户影响范围、功能重要性、修复完整性
- 用户体验类改动（即使技术简单）可提升优先级至 medium
