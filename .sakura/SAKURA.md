# astrbot_plugin_say_picture 项目概述

## 1. 项目简介

astrbot_plugin_say_picture 是一个基于 AstrBot 框架开发的 QQ 机器人插件，核心功能是让机器人能够根据用户 @指令 自动生成和发送表情包图片。该插件通过 OneBot v11 协议与 QQ 平台实现交互，支持群聊和私聊场景下的图片消息发送。

## 2. 技术栈

### 核心框架

AstrBot 框架

AstrBot 是一款模块化的 QQ 机器人框架，支持插件化扩展。开发者可通过编写插件实现自定义功能，框架提供了事件处理、消息解析、配置管理等基础能力。

### 通信协议

OneBot v11 标准

插件遵循 OneBot v11 协议规范，通过调用以下核心 API 实现消息发送功能：

send_msg - 发送消息
send_group_msg - 发送群消息
send_private_msg - 发送私聊消息

### 开发语言

Python 3.x

项目代码总量约 6145 行，采用 Python 作为主要开发语言，具备良好的跨平台兼容性和丰富的第三方库支持。

该许可证要求衍生作品必须开源，适用于网络服务场景。

```
astrbot_plugin_say_picture/
├── main.py                 # 插件主逻辑入口，核心功能实现

    ├── memory/             # 运行时内存/缓存数据
```

### 核心模块说明

main.py

插件的主逻辑文件，包含消息处理、指令解析、图片生成与发送等核心功能。插件检测用户 @提及 行为，当触发预设指令时执行图片生成流程。

metadata.yaml

插件元信息配置，定义插件名称、版本号、作者、依赖项等基本信息，框架通过此文件识别和加载插件。

_conf_schema.json

配置文件的 JSON Schema 定义，描述各配置项的类型、默认值和约束条件，用于配置验证和自动生成配置界面。

config.json

用户运行时配置文件，存储插件的可配置参数，如默认图片地址、发送格式（闪照或普通图片）等。

## 4. 开发约定

### 插件开发规范

基于 AstrBot 框架的插件开发模式，插件需提供标准的元信息配置和入口函数。main.py 中应实现框架定义的事件处理接口，响应用户消息和指令。

### 配置管理约定

插件采用 JSON Schema 规范定义配置结构，配置项包含类型声明、描述说明和默认值。_conf_schema.json 提供了配置验证能力，确保运行时配置的有效性。

### 消息交互约定

遵循 OneBot v11 协议的消息格式，图片消息采用 CQ 码或 URL 方式传输。插件支持普通图片和闪照两种发送模式，可通过配置切换。

### 目录组织约定

.sakura/ 目录用于存放运行时资源，采用 docs、memory、rules 子目录分离不同类型资源。docs/ 存放文档，memory/ 存放运行时数据，rules/ 存放业务规则。

### 许可证遵循

项目采用 AGPL-3.0 许可证，所有分发和修改需遵循开源要求。网络使用场景也需开源相关代码，贡献代码默认接受相同许可证约束。

### 5.1 Issue 分析硬性检查清单

> ⚠️ 分析时必须逐项确认，否则视为不完整

#### 附件处理（UI/坐标类必检）
- [ ] **有截图时必须查看**：明确说明是否已查看附件，确认期望位置
- [ ] 基于截图内容推断时需注明"基于图片内容推测"
- [ ] 未查看附件时，置信度应额外下调 0.05

#### 边界检查（PIL 绘图类必检）
- [ ] 文字放大后是否超出容器/气泡框边界
- [ ] 新位置是否与其他元素重叠
- [ ] 与周围元素的间距是否协调

#### 标签推荐（每次必检）
- [ ] 至少推荐 2-3 个标签，不能少于 2 个
- [ ] 分类关键词（`[bug]`、`[enhancement]`）必须识别
- [ ] 图片生成类 Issue 必须包含 `image-generation` 标签

#### 图片类 Issue 处理
- **截图价值取决于清晰度**：分析时需注明"基于图片内容推测"，存在信息损耗
- **必须查看附件**：UI/图像类 Issue 应明确说明"已查看附件确认期望位置"
- **坐标类修改建议**：在 PR 中附上不同场景的效果对比
- **边界条件**：需考虑气泡框宽度、文字长度等动态变化
- **字体放大风险**：字号从 18→28 需计算渲染宽度是否超出气泡框

#### 字体/中文支持 Issue
- **跨平台兼容性**：需列出各平台典型字体路径
  - Windows: `C:/Windows/Fonts/simhei.ttf`、`msyh.ttc`
  - macOS: `/System/Library/Fonts/PingFang.ttc`
  - Linux: 需 fontconfig 配合
- **字体回退机制**：系统字体查询 + 内置备选方案
- **置信度建议**：0.85-0.90（图片 Issue 存在解读不确定性）

#### 空标题/无效标题处理
- **策略**：必须依赖摘要生成作为 Primary 信息源
- **改写**：当原标题无信息量时，改写有必要且适当
- **输出格式**：不能出现 `<SUGGESTED_TITLE>` 等异常标记
- **降级策略**：摘要生成失败时，使用关键词提取备用方案

#### 分析健壮性要求
- **关键词匹配**：标题含 `[bug]` 等关键词必须识别，强化匹配规则
- **协议标签过滤**：摘要生成时需过滤协议标签（如 `http://`、`javascript:`）
- **容错机制**：置信度过低时不直接放弃，应给出"基于不完整信息的推断"
- **UI 问题特殊性**：坐标分析应检查目标区域可用空间、周围元素、文字大小等

### 5.5 常见问题诊断

#### 分类失败原因
- 标题含 `[bug]` 关键词却未识别 → 强化关键词匹配规则
- 摘要生成协议标签未过滤 → 添加内容安全过滤层

#### 分析流程中断应对
- 降级策略：使用关键词提取备用方案
- 增强容错机制：不因置信度过低直接放弃输出
- 当标题为空时，更应依赖摘要分析标签

#### 分析深度不足常见表现
- UI 调整风险评估偏低：需考虑视觉一致性和周围元素影响
- 未给出具体坐标建议：应提供参考坐标或说明需与用户确认
- 未考虑国际化：不同语言文字长度不同，可能需动态计算位置
- 未考虑可配置性：是否应提供配置项而非硬编码？
