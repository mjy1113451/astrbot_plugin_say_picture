# 代码审查经验总结

**累计反思 5 次**

---

## 核心经验

### 1. 分类与优先级

- **分类必须基于内容实质**：标题含 `[bug]` 却分类为 `other` 是严重错误
- **优先级多维度判断**：用户体验类改动即使技术简单，也可提升优先级（如 medium 而非 low）
- **常见分类映射**：
  - 功能请求/UI改进 → `enhancement` 或 `feature request`
  - 缺陷/错误 → `bug`
  - 空标签需强制补充

### 2. 标签体系

- **必检标签**：`bug`、`enhancement`
- **针对性标签**：`font`（字体问题）、`i18n`/`chinese`（国际化）
- **UI相关**：`ui`、`ux`、`display`
- **贡献友好**：`good-first-issue`（改动简单时考虑）
- **置信度建议**：图片类 Issue 0.85-0.90，避免过高

### 3. 可行性评估

- **必须覆盖**：
  - 具体代码行数定位
  - 目标位置的具体坐标/方案
  - 边界条件和动态场景（内容长度变化、多语言）
- **常见遗漏**：
  - 跨平台兼容性（字体路径：Windows `C:/Windows/Fonts/`、macOS `/System/Library/Fonts/`）
  - 配置化可能性
  - 文字溢出检查

### 4. 重复检测

- 需检查相关关键词和文件
- 记录检查过程便于追溯

### 5. 标题改写

- 空标题/无效标题（仅标点）必须改写
- 改写保留核心信息 + 分类前缀
- 建议格式：`[分类][优先级] 核心描述`

### 6. 摘要与信息提取

- **摘要作为 Primary 信息源**，尤其当标题无效时
- 图片类 Issue 需注明"基于图片内容推测"
- 协议标签（`http://`、`javascript:` 等）必须过滤

### 7. 降级与容错

- 分析失败时启用降级策略：关键词提取备用方案
- 不能因置信度低而直接放弃，应给出"基于不完整信息的推断"
- 增强容错机制处理边界情况

## 仓库特定模式

- AstrBot 插件项目
- 常见 Issue 类型：字体渲染、图片生成、UI位置调整
- 建议建立标签清单：`font`、`ui`、`plugin`、`good-first-issue`
