## 一、审查策略规范

### 1.1 审查模式选择

| 模式 | 适用场景 | 禁止场景 |
|------|----------|----------|
| **Full** | 首次全量审查、复杂逻辑变更 | - |
| **Quick** | 小改动(<30行)、无复杂逻辑 | 坐标计算/布局变更 |

### 1.2 首次全量审查特别要求

1. 审查策略不得降级为 Quick/Fast
2. 必须记录：项目核心功能、入口、潜在风险区
3. 变更排查范围应覆盖所有相关标识符（非仅 diff 部分）

### 1.3 Quick 模式升级触发条件

> 以下条件满足任一即强制升级：
- 代码量 > 30 行
- 涉及坐标计算/布局变更
- 涉及多步数学运算(≥5步)
- 涉及网络/存储操作
- 新增复杂计算逻辑（即使行数少）

## 二、审查质量评估维度

### 2.1 覆盖度检查清单

| 维度 | 说明 |
|------|------|
| 修复目标明确性 | PR 描述与变更是否一致 |
| 修复完整性 | 是否存在同类问题遗漏 |
| 首次审查深度 | 是否满足模式选择规范 |
| 根因验证 | 是否排查问题根源而非仅修复表象 |

### 2.2 布局/UI 变更专项检查

**必须执行**：
- □ 代入至少 3 组具体数值验证坐标计算
- □ 检查气泡高度变化时（0、正常、极端）的行为
- □ 验证相关联的 x/y 坐标同步更新
- □ 极端长度测试（单字符/50+字符）
- □ 不同头像尺寸下的坐标验证

**强烈建议**：
- □ CJK 字符宽度适配
- □ 多语言场景测试
- □ 屏幕适配（最小支持分辨率）

## 三、经验教训

### 3.1 "小改动"审查原则

| 变更大小 | 首次审查深度 | 后续审查深度 |
|----------|--------------|--------------|
| 小(<10行) | **仍需 Full** | Quick 可接受 |
| 大(>100行) | Full | Full |

**原因**：首次审查承担建立项目上下文基线的任务，改动大小不影响这一职责。

### 3.2 修复验证 ≠ 根因验证

| 验证类型 | 做法 | 目的 |
|----------|------|------|
| 修复验证 | 确认变量名已修改 | 确保修改已生效 |
| 根因验证 | 搜索所有相关引用，排查遗漏 | 防止同类问题残留 |

### 3.3 一致性 ≠ 正确性

审查通过了一致性检查（预计算变量被正确使用），但**没有验证计算逻辑本身是否正确**。对于涉及坐标计算的变更，应额外验证计算公式。

### 3.4 变量覆盖陷阱

同一作用域内重复赋值同一变量名是隐蔽的错误源。建议在代码风格建议中标注此类风险。

## 四、Issue 分析规范

### 4.1 分类与优先级

| 维度 | 规范 |
|------|------|
| 分类 enhancement | 用于纯视觉样式优化 |
| 优先级 low | 改动极小、无功能影响 |

### 4.2 重复检测要求

重复检测结果**必须**包含：
```
- 疑似重复的 Issue 涉及内容
- 相似点
- 差异点
```

### 4.3 视觉效果 Issue 处理

涉及视觉效果的 Issue，应先确认当前代码的实际效果，再分析需求。避免直接假设用户意图与代码现实的差距。

## 五、Quick 模式决策树

```
行数 ≤ 30?
├─ 否 → 升级完整审查
└─ 是 → Quick 审查
    └─ 但需验证：
        ├─ 无复杂计算链路
        └─ 若包含 ≥5 步数学运算 → 降级评分或补充测试说明
```

## 六、项目特有模式

| 模式 | 特征 | 审查关注点 |
|------|------|----------|
| PIL 图片合成 | 聊天截图生成 | 坐标计算、字体加载、临时文件 |
| 布局硬编码 | 气泡/头像/标签直接计算坐标 | 极端长度、多语言适配 |
| 尺寸预计算 | 先测量 bbox 再分配画布 | 计算逻辑正确性 |

### 6.1 标签体系

本项目使用的标签：
- `style`：视觉样式
- `PIL`：PIL 绘图相关
- `enhancement`：功能增强
- `bug`：缺陷修复

### 6.2 标题格式

Issue/PR 标题格式：`[type][priority] 简要描述`
