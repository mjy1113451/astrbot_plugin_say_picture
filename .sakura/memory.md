## 一、核心审查规范

### 1.1 增量审查策略边界

| 策略 | 适用条件 | 必须检查 | 可略过 |
|------|----------|----------|--------|
| **Quick** | 小改动、纯逻辑 | 增量功能本身 | 非核心路径 |
| **完整** | 大改动、复杂逻辑 | 全链路+副作用 | — |

**⚠️ Quick 模式的强制升级条件**（满足任一即升级）：
- 新增代码 >30 行
- 包含网络操作 + 文件系统操作
- 包含多级回退链路（≥3 级）
- 引入新的子系统
- 涉及资源下载/缓存

### 1.2 下载类操作必查清单

```
□ HTTPS 链接是否存在
□ 是否有完整性校验（SHA256/签名）
□ 是否有超时机制（建议 ≤10s）
□ 下载失败时的降级/报错策略
□ 临时文件清理机制
□ 磁盘空间不足的处理
```

### 1.3 字体/资源加载审查清单

```
□ 超时设置
□ 完整性校验（内置资源必须有 SHA256）
□ 失败日志记录
□ 内存占用评估
□ 多实例场景（是否重复加载）
□ 多级回退的每级失败处理
□ 最终兜底的退出条件
```

### 1.4 临时文件审查要点

```
□ 使用后是否显式关闭
□ 是否设置 delete=True + 异常路径验证
□ 长期运行进程是否导致 /tmp 膨胀
□ 清理失败时的兜底策略
```

### 1.5 全局状态修改检测

```
□ 是否修改模块级全局变量
□ 是否调用 setdefaulttimeout、setrecursionlimit 等全局设置函数
□ 是否修改环境变量或全局配置
□ 变更是否会传递到其他代码路径
```

## 二、常见问题模式库

### 2.1 高频风险模式

| 模式 | 风险等级 | 建议 |
|------|----------|------|
| `socket.setdefaulttimeout()` | ⚠️ 中 | 改用单次请求超时 `timeout=` |
| 函数内导入 `import socket` | ⚠️ 轻微 | 文件顶部导入更规范（除非防循环依赖） |
| 静默降级无日志 | ⚠️ 中 | 至少记录 WARNING 级别日志 |
| 魔法数字（avatar_size=90） | ℹ️ 低 | 应抽取为常量或配置 |
| `delete=True` 依赖隐式清理 | ⚠️ 中 | 显式 `shutil.rmtree` 更可靠 |

## 三、项目特有规范

### 3.1 AstrBot 插件规范

- 内置字体必须附带 SHA256 校验文件
- 网络下载字体必须 timeout ≤ 10s
- 大型资源文件（>1MB）应要求显式说明必要性
- 字体加载必须内置字体作为最高优先级

### 3.2 Issue 分析规范

| 项目 | 要求 |
|------|------|
| 分类 | 准确（enhancement/feature/bug 等） |
| 标签 | 涉及字体必须有 `font`、`PIL/pillow`、`style`/`layout` |
| 标题 | 异常标题（仅符号）必须改写 |
| 可行性 | 分析失败时应重试或标记"待人工处理"，非"无法评估" |

## 四、审查质量评估框架

### 4.1 评分标准

| 问题严重程度 | 描述 | 影响 |
|--------------|------|------|
| **Critical** | 功能完全不可用或安全漏洞 | 阻塞合并 |
| **Medium** | 部分功能受损或风险存在 | 建议修复 |
| **Low/Minor** | 代码质量、风格问题 | 可接受 |

### 4.2 评分与决策一致性检查

```
评分 3-4/10 → 通常对应 request_changes（有明确问题）
评分 6-7/10 → 通常对应 request_changes（有多个问题）
评分 8-9/10 → 通常对应 Approve（有小瑕疵）

⚠️ 若评分与决策不一致（如 6/10 + Approve），需在报告中说明
```

## 五、经验教训汇总

### 5.1 Quick 模式边界教训

1. **不能跳过安全敏感操作**：网络请求、文件下载、临时资源创建
2. **不能跳过回退链路验证**：即使只看增量，全局副作用仍需评估
3. **隐藏子系统的识别**：当函数内新增网络+文件操作时，应降级评分或升级策略

### 5.2 功能性 ≠ 安全性

- 功能实现正确 ≠ 安全性合格
- 字体下载功能正常 ≠ 无安全风险（缺少完整性校验）
- 评分应反映**实际发现的问题数量和严重程度**

### 5.3 Issue 分析质量要点

- 异常标题必须改写，不得标记"无建议"
- 分析流程失败时应重试或标记"待人工处理"
- 标签体系需遵循项目规范

## 六、持续改进方向

1. **审查报告模板升级**：发现全局状态修改时，强制要求说明影响范围

3. **建议采纳跟踪**：记录未被采纳的改进建议，后续审查时重新评估
4. **Issue 分析二次验证**：确保标签、分类、标题均符合规范
